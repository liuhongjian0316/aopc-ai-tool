# 全周期开发

按「澄清 → 方案 → 拆解 → 实现 → 自检 → 交付」六步推进。小需求（改动 < 3 个文件且思路唯一）可合并前两步，但澄清和自检不可跳过。

## 1. 需求澄清

- 先读项目档案（项目根 `.wudi/project.json`，没有则先了解技术栈再建议 `/wudi` 建档）。
- 用一句话复述需求，确认「成功标准」：做完后用什么验证（可运行的命令 / 可见的页面 / 通过的测试）。
- 有歧义时列出假设让用户挑选，而不是开放式追问；最多问 3 个问题。
- 明确「不做清单」：本次明确不做的相邻功能，写进方案防蔓延。

## 2. 技术方案

- 先找可复用的：搜现有实现、工具函数、相似模式，能改就不新建。
- 给 2~3 个方案，每个一段话：核心思路 + 优点 + 代价，末尾给明确推荐和理由。
- 标注影响面：会动的模块、接口签名变化、数据/配置迁移、需要同步改的调用方与测试。
- 方案经用户确认后再动手；用户说「直接做」的紧急小改动可跳过对比，但要在实现前一句话说明选择。

## 3. 任务拆解

- 拆成每步可独立验证的小任务，粒度标准：一个任务 = 一次可跑通的改动 + 一句验证方式。
- 顺序原则：先数据/接口层，后 UI；先骨架后细节；每步结束是可运行状态。
- 复杂任务（> 8 步）建议交给 `wudi-architect` 子代理产出拆解清单再执行。

## 4. 实现

- 写之前先读目标文件的邻居代码：命名、注释密度、错误处理风格向周围看齐，不顺手大改无关风格。
- 提交粒度：一个任务一次 commit，信息写「做了什么 + 为什么」。
- 错误处理：对外接口必须有兜底（返回错误结构而不是崩溃）；内部工具函数可以快速失败。
- 不确定第三方 API 行为时查文档或写最小验证脚本，不凭记忆写。

## 5. 自检（不可跳过）

逐项过，如实报告结果，失败项修完再继续：

- [ ] 构建/编译通过（项目档案的 build 命令）
- [ ] lint / 类型检查通过（如有）
- [ ] 相关测试通过；没有测试的核心改动补最小测试
- [ ] 手动走一遍主路径 + 一个边界（空输入 / 异常分支）
- [ ] `grep` 检查是否漏改调用方（改了签名/路径/配置键时）

## 6. 交付

- 汇总：改了什么、验证结果、遗留风险（一句话一条）。
- 衔接建议：功能完成 → `/wudi-docs` 补文档；要上线 → `/wudi-deploy`；需要第三方视角 → 让 `wudi-reviewer` 子代理评审。

## 大型任务：团队并行模式

任务拆解超过 8 步且分片之间**无共享文件依赖**时，进入团队模式（或直接由 `/wudi-team` 触发）：

1. **先串行产出拆解**：让 `wudi-architect` 子代理出完整方案与分片清单，每个分片标注：改动文件范围、接口契约（分片间的函数签名/数据结构必须先冻结）、验证命令。
2. **接口契约冻结**：共享类型/接口/配置先由主对话实现并提交，再并行 —— 这是并行不出冲突的前提。
3. **并行派发**：无依赖的分片同时派给多个实现子代理，每个子代理的指令必须包含：只改哪些文件（白名单）、接口契约、验证命令；明确禁止改动白名单外的文件。
4. **逐片验证**：每个子代理返回后立刻跑其验证命令，失败就单独修该分片，不带病合入下一片。
5. **集成收口**：全部分片合入后主对话跑整体自检（第 5 步清单）+ `wudi-reviewer` 交叉评审。

红线：共享文件（同一目录的索引/路由/入口）的分片一律串行；并行子代理数量 ≤ 4；任何子代理的报告只当线索，验证以命令结果为准。

## 红线

- 不在未经确认的情况下删数据、改数据库结构、动线上配置。
- 测试失败不许靠改断言糊弄过去；要么是真 bug 修掉，要么说明为什么断言该改。
- 不为「能跑」引入明显的技术债（全局变量、吞异常、复制粘贴大段代码）而不告知用户。
