# 项目文档

核心原则：**文档从真实代码和状态提取，不编造**。接口签名、配置项、命令必须来自当前代码，写不出来就去读代码，读不出来说明代码缺信息，先补代码注释再补文档。

## 文档矩阵

| 类型 | 触发时机 | 信息来源 |
| --- | --- | --- |
| README | 项目建档 / 重大变更 | 项目档案 + 入口代码 + package 清单 |
| API 文档 | 接口增删改 | 路由定义 / handler 签名 / 请求响应结构体 |
| PRD | 新功能立项 | 需求对话 + `wudi-architect` 方案产出 |
| 部署手册 | 接入部署 / 环境变更 | `.wudi/project.json` + 服务器侧配置实况 |
| CHANGELOG | 每次版本发布 | git log + 本次会话改动汇总 |
| 架构文档 | 模块数 / 5 或目录大调整 | 目录结构 + 依赖关系实际梳理 |

生成前先看 `docs/` 里已有什么：**更新优先于新建**，格式向已有文档看齐。

## 各类型要点

- **README**：一段话定位 → 快速开始（可复制即跑的命令）→ 目录结构 → 常用命令表 → 部署一句话 + 指向部署手册。不写空洞口号，不堆徽章。
- **API 文档**：每个接口：方法 + 路径 + 权限 + 请求/响应示例（真实结构）+ 错误码表。从路由注册处顺藤摸瓜，不凭对话记忆写。
- **PRD**：背景与目标 → 用户故事（作为 X 我要 Y 以便 Z）→ 功能范围（做/不做清单）→ 验收标准（可勾选）→ 里程碑。与 wudi-dev 技能的「成功标准」呼应。
- **部署手册**：服务器要求 → 首次部署步骤 → 日常发布（引用流水线命令）→ 回滚步骤 → 故障排查（引用 wudi-deploy 技能清单）→ 环境变量表。每条命令必须是在档案对应服务器上真实可执行的。
- **CHANGELOG**：按 Keep a Changelog 格式，Added/Changed/Fixed/Removed 分组，面向使用者写（不说重构了内部类，说 X 场景更快/修复 Y 报错）。

## 落盘与登记

- 文档写到项目 `docs/`（README 例外，在根目录）。
- 有 `wudi_status` MCP 工具时用 `docsRegister` 登记生成结果（面板文档库可见）；没有时更新 `.wudi/docs.json` 清单（`{ "path": "docs/api.md", "type": "api", "updatedAt": "...", "source": "route scan" }`）。

## 导出

需要交付格式（docx/pptx/xlsx/pdf）时：markdown 先写好，再用宿主对应技能（`docx` / `pptx` / `xlsx` / `pdf`）转换；转换后如实告知用户产物路径。宿主技能不可用时说明并给出手动转换建议。

## 维护节奏

完成这些事件后主动提醒更新对应文档：接口变更 → API 文档；功能上线 → CHANGELOG + README；部署方式变更 → 部署手册。用户拒绝更新就不再纠缠，但要指出文档已滞后的事实。
